================================================================================
  1. PURPOSE
================================================================================

  This document defines the file conventions and coding standards for
  all files in the HobbyCAD project family.  Every version-controlled
  file must follow the header format for its file type.

  The project spans multiple repositories:

    Local Directory     GitHub Repository           Description
    ───────────────     ─────────────────           ───────────
    HobbyCAD/           ayourk/hobbycad             Main application
    HobbyCAD-vcpkg/     ayourk/hobbycad-vcpkg       vcpkg custom registry
    HobbyCAD-homebrew/  ayourk/homebrew-hobbycad     Homebrew tap
    HobbyCAD-libs/      not in any repo              PPA library packaging
    HobbyCAD-outside/   not in any repo              Session docs, notes

  All repos live under /wd8tb/ai/hobbycad/ on the developer's machine.
  Binary files (images, archives, compiled objects) are NOT stored
  in the main HobbyCAD repository.  HobbyCAD-libs stores tarballs
  and source packages alongside debian packaging.

  Goals:
    - Every file is self-identifying (path, purpose, license)
    - Consistent style across the entire project tree
    - Easy to navigate by both humans and tools
    - grep-friendly for locating files by path or purpose

================================================================================
  2. FILE HEADER FORMAT
================================================================================

  Every file begins with a header block that includes:

    1. A visual separator line (comment style depends on file type)
    2. The repository name (local directory name)
    3. The file's relative path from the repository root
    4. A short dash-separated title describing the file's purpose
    5. An optional longer description (2-5 lines)
    6. SPDX license identifier (see Section 6 for definition)
    7. A closing separator line

  The repository and relative path are the FIRST meaningful content
  in the header.  This makes it possible to identify any file's home
  repository and location by viewing the first few lines, even if it
  has been copied or moved.

  For files stored outside of all repositories, use:
    "not in any repo"
  in place of the repository name.


  2.1  C++ SOURCE FILES (.cpp)
  -----------------------------

    // =====================================================================
    //  HobbyCAD — src/hobbycad/gui/clipanel.cpp — Embedded CLI terminal panel
    // =====================================================================
    //
    //  Optional multi-line description of the file's purpose.
    //  Keep to 2-5 lines maximum.
    //
    //  SPDX-License-Identifier: GPL-3.0-only
    //
    // =====================================================================

  Rules:
    - Separator line: exactly 69 characters (// + space + 65 '=' chars)
    - Path line: //  RepoName — path/from/root.cpp — Short Title
    - The em-dashes (—) separate repo, path, and title
    - SPDX line is always present
    - Blank comment line before and after the description block


  2.2  C++ HEADER FILES (.h)
  ---------------------------

  Same format as .cpp files, followed by the include guard:

    // =====================================================================
    //  HobbyCAD — src/hobbycad/gui/clipanel.h — Embedded CLI terminal panel
    // =====================================================================
    //
    //  Description of the class or module.
    //
    //  SPDX-License-Identifier: GPL-3.0-only
    //
    // =====================================================================

    #ifndef HOBBYCAD_CLIPANEL_H
    #define HOBBYCAD_CLIPANEL_H

    ...

    #endif  // HOBBYCAD_CLIPANEL_H

  Include guard naming: HOBBYCAD_FILENAME_H (uppercase, underscores).
  Always use #ifndef/#define, not #pragma once (portability).


  2.3  CMakeLists.txt
  --------------------

    # =====================================================================
    #  HobbyCAD — src/hobbycad/CMakeLists.txt — HobbyCAD Application
    # =====================================================================
    #
    #  Description of what this build file produces.
    #
    # =====================================================================

  Rules:
    - Hash (#) comment style
    - Same separator width (69 characters including # and space)


  2.4  SHELL SCRIPTS (.sh)
  -------------------------

    #!/bin/bash
    # =====================================================================
    #  HobbyCAD — tools/linux/build-appimage.sh — AppImage Build Script
    # =====================================================================
    #
    #  Description of what the script does.
    #
    #  SPDX-License-Identifier: GPL-3.0-only
    #
    # =====================================================================

  Rules:
    - Shebang (#!/bin/bash) is always the first line
    - Header block immediately follows the shebang
    - Scripts must be executable (chmod +x)


  2.5  QT STYLESHEETS (.qss)
  ----------------------------

    /* =====================================================================
     *  HobbyCAD — resources/themes/darkmode.qss — Built-in Dark Mode
     * =====================================================================
     *
     *  Repository: HobbyCAD (ayourk/hobbycad)
     *  File: resources/themes/darkmode.qss
     *
     *  Description of the theme or stylesheet.
     *
     *  SPDX-License-Identifier: GPL-3.0-only
     *
     * ===================================================================== */

  Rules:
    - CSS block comment style: /* ... */
    - Each interior line starts with " * " (space-star-space)
    - Separator lines: " *  " + 65 '=' characters
    - Include a "Repository:" and "File:" line for quick identification
    - Section headers within the file use the same block comment style


  2.6  PLAIN TEXT DOCUMENTS (.txt)
  ---------------------------------

    ================================================================================
      HobbyCAD — DOCUMENT TITLE IN CAPS
    ================================================================================

      Project          : HobbyCAD
      Repository       : HobbyCAD (ayourk/hobbycad)
      File             : docs/filename.txt
      Document Version : 0.0.1
      Date             : YYYY-MM-DD

      AI Attribution   : This document was primarily generated with
                         the assistance of Claude AI (Anthropic).
                         Human review and editorial direction provided
                         by the project author.

  Rules:
    - Separator: 80 '=' characters
    - Title: indented 2 spaces, ALL CAPS
    - Metadata block: Project, Repository, File, Document Version, Date
    - Repository uses the local directory name with GitHub name in parens
    - For files outside all repos: "Repository : not in any repo"
    - AI Attribution block when applicable
    - Section headers: indented 2 spaces, numbered, ALL CAPS
    - Subsection headers: indented 2 spaces, numbered, Title Case
    - Body text: indented 4 spaces
    - Line width: 80 characters maximum


  Punctuation: no em dash and no ASCII double hyphen as prose
  punctuation, in any document, comment or commit message.  Use a
  colon, a semicolon, a comma or parentheses.  The em dash (—) stays
  where a convention prescribes it as a separator, the file-header path
  line above and section headings; "--" is written only as part of a
  command-line switch.

  2.7  MARKDOWN FILES (.md)
  --------------------------

    # Title

    <!-- HobbyCAD — README.md -->

    Content begins here.

  Rules:
    - Standard Markdown heading with #
    - HTML comment with repo name and file path on the third line
    - No separator lines (Markdown's own formatting suffices)


  2.8  SVG FILES (.svg)
  ----------------------

    <?xml version="1.0" encoding="UTF-8"?>
    <!--
      HobbyCAD — resources/icons/hobbycad.svg — Application Icon

      Optional multi-line description.

      SPDX-License-Identifier: GPL-3.0-only
    -->
    <svg ...>

  Rules:
    - XML declaration on the first line
    - HTML/XML comment block immediately after
    - Repo name, file path, and title on the first line of comment
    - SPDX identifier inside the comment block


  2.9  XPM FILES (.xpm)
  ----------------------

    No XPM is committed. The Debian menu icon (share/pixmaps/
    hobbycad.xpm, 32x32) is rendered from resources/icons/hobbycad.svg
    at build time by tools/render-icons.cpp through Qt's XPM writer,
    so it is a build artifact: no header block, no hand edits. Change
    the SVG instead.


  2.10  DATA/CONFIG FILES (AUTHORS, .gitignore, etc.)
  -----------------------------------------------------

  Files without a natural comment syntax use the plain text document
  format where possible:

    ================================================================================
      HOBBYCAD / HOBBYMESH — AUTHORS
      Repository: HobbyCAD (ayourk/hobbycad)
      File: AUTHORS
    ================================================================================

  For .gitignore:

    # =====================================================================
    #  HobbyCAD — .gitignore — Version control exclusions
    # =====================================================================

  For files that cannot contain comments (JSON, etc.), the file path
  and purpose should be documented in the nearest README.txt.

================================================================================
  3. FILE NAMING CONVENTIONS
================================================================================

  Source code:
    - All lowercase
    - No underscores in filenames (e.g., climode.cpp, not cli_mode.cpp)
    - Header and source share the same base name (climode.h, climode.cpp)
    - Exception: compound names use no separator (viewportwidget.cpp)

  Documents:
    - Lowercase with underscores (project_definition.txt)
    - Plain text format (.txt) for all project documentation
    - Exception: README.md (Markdown for GitHub rendering)

  Themes:
    - Lowercase with underscores (dark_blue.qss)
    - .qss extension (Qt stylesheet)
    - The built-in default.qss and darkmode.qss in resources/themes/ are
      the reference: every setObjectName() widget appears in them

  Build files:
    - CMakeLists.txt (CMake standard)
    - Uppercase README.txt for stub directories

  Shell scripts:
    - Lowercase with hyphens (build-appimage.sh)

  Icons:
    - Canonical source is SVG (hobbycad.svg)
    - The build-rendered XPM keeps the base name (hobbycad.xpm)
    - Sized PNGs use base name + hyphen + size (hobbycad-48.png)
    - Platform icons: .ico (Windows), .icns (macOS)
    - PNGs, .ico, and .icns are generated at build time from SVG
      and should NOT be committed to version control

  5. OBJECT NAMING (setObjectName) CONVENTION
================================================================================

  Every QWidget subclass that could be targeted by a theme stylesheet
  must call setObjectName() in its constructor.

  Naming rules:
    - PascalCase (e.g., CliPanel, FeatureTree)
    - Descriptive of the widget's role, not its class
    - Suffix "Dock" for QDockWidgets (e.g., TerminalDock)
    - No prefix (no "m_", no "hobbycad_")

  When adding a new widget:
    1. Call setObjectName() with a PascalCase name
    2. Add the name to docs/theming.txt Section 2
    3. Add a section for it in resources/themes/default.qss and
       darkmode.qss
    4. Update this document's directory tree if a new file was added

  Current object names are listed in docs/theming.txt.

  6. LICENSE HEADERS

  6.1  SPDX License Identifiers
  -------------------------------

  SPDX (Software Package Data Exchange) is an open standard maintained
  by the Linux Foundation for communicating software license information.
  Rather than including the full license text in every file, SPDX
  defines short, machine-readable identifiers for common licenses.

  The SPDX specification is maintained at:
    https://spdx.org/licenses/

  HobbyCAD uses the following SPDX identifier:

    SPDX-License-Identifier: GPL-3.0-only

  This means: GNU General Public License version 3.0, and only
  version 3.0 (not "or later").  The full license text is in the
  LICENSE file at the project root.

  The SPDX identifier serves as a compact, legally recognized way to
  state the license.  It is understood by license scanners (REUSE,
  FOSSology, ScanCode), package managers, and repository hosting
  services (GitHub, GitLab).

  6.2  Placement
  ---------------

  The SPDX identifier is placed in the file header block (see
  Section 2) on its own line:

    //  SPDX-License-Identifier: GPL-3.0-only

  6.3  Exemptions
  ----------------

  Files that are not copyrightable (e.g., .gitignore patterns,
  trivial data files) do not need a license header.

  Third-party files retain their original license headers and are
  documented in AUTHORS.

  6.4  Developer Certificate of Origin (DCO)
  --------------------------------------------

  All commits to HobbyCAD repositories must include a Signed-off-by
  trailer certifying that the contributor has the right to submit
  the code under the project's license.  This follows the Developer
  Certificate of Origin (https://developercertificate.org/), the
  same mechanism used by the Linux kernel.

  Commit Message Approval:  When working with AI assistants (e.g.,
  Claude Code), commit messages must be presented to and approved
  by the user before any commit is made.  The AI assistant does not
  commit on the author's behalf.  See Section 6.6 for the message
  format.

  The sign-off is a single line at the end of the commit message:

    Signed-off-by: Your Name <your.email@example.com>

  How to sign off:

    Command line:     git commit -s
                      git commit --signoff

    Fix past commits: git rebase --signoff HEAD~N

    Make it default:  git config --global format.signoff true

  GitHub's web interface will add the trailer automatically when
  the "Require contributors to sign off on web-based commits"
  setting is enabled (configured per-repository).

  CI enforcement:

    .github/workflows/dco.yml runs on every pull request and
    rejects any commit missing a valid Signed-off-by trailer.
    The check is required to pass before merging.

  6.5  GPG Commit Signing (Verified Commits)
  -------------------------------------------

  All commits to HobbyCAD repositories must be GPG-signed.  GitHub
  displays a "Verified" badge on signed commits, confirming the
  commit was made by the account holder.

  Setup:

    1. Generate a GPG key (if you don't have one):

         gpg --full-generate-key

       Choose RSA 4096-bit, set expiration as desired, and use
       the same email address as your GitHub account.

    2. Get your key ID:

         gpg --list-secret-keys --keyid-format=long

       The key ID is the hex string after "sec rsa4096/" (e.g.,
       3CE8B9D148CBBD08EA680D8201844DAF2500B0AC).

    3. Configure git to use the key:

         git config --global user.signingkey YOUR_KEY_ID
         git config --global commit.gpgsign true

    4. Add the public key to GitHub:

         gpg --armor --export YOUR_KEY_ID

       Copy the output (including BEGIN/END lines) and paste it
       into GitHub → Settings → SSH and GPG keys → New GPG key.

    5. Ensure the email in your GPG key matches a verified email
       on your GitHub account (Settings → Emails).

  Verification:

    Check if a commit is signed:

      git log --show-signature -1

    The output should show "Good signature from ...".

  Troubleshooting:

    - "Unverified" on GitHub: The GPG key email must match a
      verified email on your GitHub account.

    - Co-Authored-By trailers are not allowed.  They cause commits
      to show as "Unverified" when referencing emails not associated
      with verified GitHub accounts (including AI assistants).

    - If gpg-agent isn't caching your passphrase, add to ~/.bashrc:

        export GPG_TTY=$(tty)


  6.6  Commit Message Format
  ---------------------------

  Commits in this project are consolidated and condensed: one commit
  usually carries a period of work spanning several areas, rather than
  being split one commit per feature.  The message is therefore the
  only record that a given change landed at all, and it is written to
  be read years later by someone who was not there.

  Structure:

    Line 1      Subject.  Imperative mood, 72 characters or fewer,
                capitalized, no trailing period, no area prefix.
    Line 2      Blank.  Always.  Without it the entire opening
                paragraph is taken as the subject.
    Body        Overview paragraph, then sections by area.
    Last line   Signed-off-by, after a blank line.

  The subject names the changes carrying the most weight, in
  descending order of importance, until it runs out of room.  On a
  consolidated commit it will not cover everything; that is
  expected, and the body covers the rest.  A subject that would fit
  any commit in the repository, such as "Various improvements" or
  "Update multiple components", is worse than one that honestly
  names three changes out of five.

  The guiding rule for the body:

      Exhaustive at the feature level; silent at the file level.

  Condensed means condensed.  "Consolidated" says how many commits
  there are; "condensed" says how long the message is, and the second
  is the one that erodes.  The tests, applied to every bullet:

    - One bullet per area, and a bullet is a statement of a few
      sentences, not a paragraph of particulars.  A section that
      needs five bullets is describing five files, not five features.

    - If a sentence can be recovered from the diff, cut it.  What
      remains is the why, the trap, the behavior change and the
      verification, which the diff cannot give.

    - If a bullet cannot be understood without a file name, the
      statement is too fine-grained; name the outcome instead.
      Version pins, build-script mechanics and per-platform fixes
      collapse to one line each, or to nothing.

    - A draft that grows past the point where the author would read
      it end to end is the long form.  The long form is kept beside
      the running list as commit-verb.txt for reference and is never
      what gets committed; the committed message is the short form
      written from it.

  "Silent at the file level" forbids an inventory of what changed.  It
  does not forbid naming a file that is itself the subject of a
  statement: the header whose presence misleads a portability test,
  or the script whose behavior changed.  Those carry information that
  nothing else records.

  When the point is instead to send the reader somewhere, name the
  DIRECTORY rather than the paths inside it: "see docs/", not a list of
  three document names.  A directory stays correct when a file is
  renamed, and the reader can find the right document once they are in
  the right place.

  What belongs in the body:

    - An orienting paragraph of two to four sentences before any
      bullets, so that the sections following it are legible.

    - Why a change was made.  The diff already shows what changed,
      and can never show why.

    - Features added or overhauled, described by what they do for
      the user rather than by which files were touched.

    - Non-obvious constraints and traps discovered along the way.
      These are the highest-value lines in any message, because
      nothing else records them.

    - What was verified, and how.

    - Deliberate omissions, and alternatives that were rejected.

    - Behavior changes a user would notice.

  What does not belong:

    - Co-Authored-By, or any AI attribution trailer.  The
      Signed-off-by names the project author and nobody else.
      See Section 6.5.

    - A file-by-file inventory.  "git show --stat" does that better
      and cannot fall out of date.

    - Session narration: what was attempted first, then second.
      Record a dead end only when doing so stops someone from
      retrying it.

    - Status, TODO items, or next steps.  The commit is permanent
      and status is not; nothing will ever come back to correct it.

    - Superlatives: comprehensive, robust, significantly improved.

    - Facts that will become false, such as version numbers of
      components this commit did not change.

    - A first body line that restates the subject.

  Internal changes with no user-visible face (refactors,
  dependency sweeps, build script fixes) earn a mention only when
  they change behavior, remove a hazard, or explain why other work
  became possible.  Otherwise they are a single line, or absent.

  Sections are ordered by significance, not by chronology or
  alphabet.  Body text wraps at 72 columns, because "git log"
  indents its output by four spaces and 76 still fits an
  80-column terminal.

  Lifecycle:

    commit-verb.txt is a RUNNING LIST.  Entries are added as work is
    completed, rather than the whole message being composed at the
    end, so that nothing is lost between making a change and
    committing it.

    At commit time the file has served its purpose and becomes
    disposable.  The message is committed, the file is cleared, and
    it starts accumulating again for the next commit cycle.  It is
    a working document, not an archive; the committed message is
    the permanent record.

    For the same reason it is exempt from the backup policy: no
    copies of commit.txt are kept in backups/.

    The point of recording as you go is completeness, not order.
    What matters is that nothing is missing when the message is
    approved; the sequence entries were added in does not matter,
    because the file is organized before the commit anyway.

    That final pass groups the entries into sections, orders those
    sections by significance, and adds the subject and the opening
    paragraph.  Those two can only be written once the full scope
    is known, which is not true until the work stops.

  Preparation and review:

    The message is written to commit.txt in the workspace directory
    ABOVE the repository, not inside it, so that it can never be
    committed by accident.  It is reviewed by the project author before
    any commit is made, then committed with:

        git commit -F ../commit.txt

    The Signed-off-by trailer is written into commit.txt itself, so
    "-s" is not used and the trailer is not duplicated.  Because the
    message never passes through shell quoting, internal double
    quotes are fine and wording need not be contorted to avoid them.

================================================================================
  7. INCLUDE ORDER
================================================================================

  C++ source files use this include order, with each group separated
  by a blank line:

    1. Own header ("viewportwidget.h")
    2. Project headers from same module ("climode.h", "clihistory.h")
    3. Project headers from other modules (<hobbycad/core.h>)
    4. OCCT headers (<AIS_InteractiveContext.hxx>)
    5. Qt headers (<QWidget>, <QString>)
    6. Standard library headers (<iostream>, <cstdlib>)

  Example:

    #include "viewportwidget.h"

    #include <hobbycad/core.h>
    #include <hobbycad/document.h>

    #include <AIS_Shape.hxx>
    #include <V3d_View.hxx>

    #include <QMouseEvent>
    #include <QWidget>

    #include <iostream>

  Headers use angle brackets for installed/system headers and quotes
  for project-relative headers.

================================================================================
  8. GENERAL C++ STYLE
================================================================================

  Language standard:   C++17
  Naming:
    - Classes:         PascalCase          (CliEngine, ViewportWidget)
    - Functions:       camelCase           (buildPrompt, fitAll)
    - Member vars:     m_camelCase         (m_history, m_viewer)
    - Local vars:      camelCase           (nativeHandle, topColor)
    - Constants:       UPPER_SNAKE_CASE    (HOBBYCAD_VERSION)
    - Enum values:     PascalCase          (AIS_Shaded)
    - Namespaces:      lowercase           (hobbycad)
    - File names:      lowercase, no sep   (climode.cpp)

  Braces:              Next line for functions, same line for control flow

    void MyClass::doThing()
    {
        if (condition) {
            ...
        } else {
            ...
        }
    }

  Indentation:         4 spaces, no tabs
  Line width:          Soft limit 80, hard limit 100
  Namespace closing:   }  // namespace hobbycad

  Class layout order:
    1. public
    2. signals (Qt)
    3. public slots (Qt)
    4. protected
    5. private slots (Qt)
    6. private

  Pointer style:       Type* name  (star with type, not name)

    Type* ptr;            // yes
    Type *ptr;            // no

  Auto:                Use when the type is obvious from context

    auto* widget = new QLineEdit(this);   // obvious
    auto result = engine->execute(line);  // obvious from RHS
    int count = list.size();              // prefer explicit for primitives

================================================================================
  8.1 UNITS AND MEASUREMENTS
================================================================================

  Storage Convention
  ------------------

  **All internal length measurements use millimeters (mm) as the base unit.**

  This applies to:
    - All in-memory data structures (sketches, constraints, entities)
    - All save file formats (.hcad project files)
    - All library APIs (libhobbycad functions)
    - All internal calculations

  The mm convention:
    - Simplifies internal calculations (no conversion needed)
    - Provides consistent precision across unit systems
    - Matches OpenCASCADE's internal unit (mm)
    - Enables lossless unit switching in the UI

  Display Conversion
  ------------------

  Unit conversion to the user's preferred display unit happens ONLY at
  the GUI layer, using the utilities in hobbycad/units.h:

    LengthUnit         Index    Scale Factor
    ───────────────    ─────    ────────────
    Millimeters        0        1.0
    Centimeters        1        10.0
    Meters             2        1000.0
    Inches             3        25.4
    Feet               4        304.8

  Converting for display:

    #include <hobbycad/units.h>

    double mm_value = 25.4;  // Internal value in mm
    double display = mmToUnit(mm_value, LengthUnit::Inches);  // = 1.0

  Converting user input to storage:

    double user_value = 2.0;  // User entered "2 in"
    double mm = unitToMm(user_value, LengthUnit::Inches);  // = 50.8

  The Document Settings dialog allows users to select their preferred
  display unit.  This preference is stored per-project but does NOT
  affect how values are stored, only how they are displayed.

  Numeric Precision
  -----------------

  HobbyCAD uses consistent precision for all numeric values:

    Context              Decimal Places    Rationale
    ─────────────────    ──────────────    ─────────────────────────────
    File storage         15                Full double precision
    Display (UI)         up to 4           Trailing zeros trimmed

  Storage precision (15 digits) preserves the full precision of IEEE 754
  double-precision floating point numbers (~15-16 significant digits).
  This exceeds OpenCASCADE's internal tolerance (Precision::Confusion =
  10⁻⁷ mm) and any practical manufacturing tolerance.

  Display values show up to 4 decimal places, with trailing zeros removed
  for cleaner display (e.g., "1.5000" → "1.5", "45.0000°" → "45°").

  Use the functions from hobbycad/units.h:

    formatValue(value);                    // Numeric display (trims zeros)
    formatValueWithUnit(mm, unit);         // With unit suffix (e.g., "25.4 mm")
    formatAngle(degrees);                  // With degree symbol (e.g., "45°")
    formatStorageValue(value);             // For file I/O (15 decimal places)
    parseValueWithUnit(input, default);    // Parse user input to mm

================================================================================
  8.2 LIBRARY TYPE CONVENTIONS
================================================================================

  Library API Types
  -----------------

  The library (libhobbycad) uses Qt-free types in its public API:

    Qt Type          Library Type         Header
    ───────────      ──────────────       ─────────────────────
    QPointF          Point2D              hobbycad/types.h
    QRectF           Rect2D               hobbycad/types.h
    QVector3D        Vec3                 hobbycad/types.h
    QVector<T>       std::vector<T>       <vector>
    QString          std::string          <string>
    QPolygonF        std::vector<Point2D> hobbycad/types.h
    qFuzzyCompare    fuzzyCompare         hobbycad/types.h
    qFuzzyIsNull     fuzzyIsNull          hobbycad/types.h
    qMin/qMax/qAbs   std::min/max/abs    <algorithm>/<cmath>
    QString::number  formatDouble         hobbycad/format.h
    QString::arg     format               hobbycad/format.h

  Rules:
    - Library headers (.h in src/libhobbycad/) must NOT include
      Qt headers except behind #if HOBBYCAD_HAS_QT guards
    - Library source files (.cpp) may use Qt behind guards for
      I/O features (JSON, image loading, OpenGL probing)
    - GUI code (src/hobbycad/) may use Qt types freely
    - At the GUI/library boundary, Point2D/Rect2D/Vec3 convert
      implicitly to/from QPointF/QRectF/QVector3D
    - For containers: use toQVector()/fromQVector() from qt_compat.h
    - For strings: use toQt()/fromQt() from qt_compat.h

  Container Helpers
  -----------------

  The library provides Qt-style convenience functions for
  std::vector in hobbycad/types.h:

    hobbycad::contains(vec, value)    // like QVector::contains
    hobbycad::indexOf(vec, value)     // like QVector::indexOf
    hobbycad::removeOne(vec, value)   // like QVector::removeOne
    hobbycad::removeAll(vec, value)   // like QVector::removeAll
    hobbycad::removeAt(vec, index)    // like QVector::removeAt
    hobbycad::valueAt(vec, index)     // like QVector::value(i, default)

  HOBBYCAD_HAS_QT Macro
  ----------------------

  The macro HOBBYCAD_HAS_QT (defined in hobbycad/types.h) is set
  to 1 when Qt 6.4.2+ is available, 0 otherwise.  Use it to guard
  Qt-dependent code in library files:

    #if HOBBYCAD_HAS_QT
    #include <QJsonObject>
    QJsonObject toJson() const;
    #endif

================================================================================
  9. INTERNATIONALIZATION (i18n) AND TRANSLATION
================================================================================

  9.1  Overview
  --------------

  HobbyCAD uses Qt's built-in internationalization system.  English is
  the default language: all user-visible strings in source code are
  written in English and wrapped in tr().  Translations are maintained
  as XML source files (.ts) edited by translators, compiled to binary
  files (.qm) by lrelease, and loaded at runtime.

  9.2  The tr() Function
  -----------------------

  Every user-visible string MUST be wrapped in tr():

    // Correct:
    m_statusLabel->setText(tr("Ready"));
    auto* fileMenu = menuBar()->addMenu(tr("&File"));
    setWindowTitle(tr("About HobbyCAD"));

    // Wrong (not translatable):
    m_statusLabel->setText("Ready");
    m_statusLabel->setText(QStringLiteral("Ready"));

  Use QStringLiteral() only for strings that are NOT user-visible:
  object names, internal identifiers, file extensions, format strings
  consumed by code.

    setObjectName(QStringLiteral("CliPanel"));    // not user-visible
    QStringLiteral("*.brep");                     // file filter pattern

  9.3  Context and Disambiguation
  --------------------------------

  tr() uses the enclosing class name as the translation context.
  If the same English string appears in multiple classes with different
  meanings, add a disambiguation comment:

    // In FileMenu:
    tr("Open", "menu action: open a file")

    // In NetworkDialog:
    tr("Open", "connection state: port is open")

  9.4  Plurals
  -------------

  Use tr() with %n for plural forms:

    tr("%n shape(s) loaded", "", count)

  Qt's translation system handles complex plural rules for languages
  that have more than two plural forms (e.g., Russian, Arabic).

  9.5  Translation Workflow
  --------------------------

  Source files (.ts) live in resources/translations/:

    resources/translations/
      hobbycad_en.ts         English (reference, generated, not edited)
      hobbycad_de.ts         German
      hobbycad_fr.ts         French
      hobbycad_ja.ts         Japanese
      hobbycad_pirate.ts     Pirate English (fun/community language)

  Workflow:

    1. Developer writes code with tr() strings
    2. Run lupdate to extract strings into .ts files:

         lupdate src/ -ts resources/translations/hobbycad_en.ts

    3. Translator edits .ts files using Qt Linguist or a text editor
       (.ts files are human-readable XML)
    4. Run lrelease to compile .ts -> .qm:

         lrelease resources/translations/hobbycad_pirate.ts

    5. .qm files are embedded into the binary via the .qrc resource
       file, or installed alongside the application

  9.6  Loading Translations at Runtime
  --------------------------------------

  The application loads translations at startup in main.cpp:

    // 1. Try user-selected language from preferences
    // 2. Fall back to system locale
    // 3. Fall back to English (built-in, no translation needed)

    QTranslator translator;
    QString locale = preferredLanguage();  // from settings
    if (locale.isEmpty()) {
        locale = QLocale::system().name(); // e.g., "de_DE"
    }

    // Try embedded resource first, then external file
    if (translator.load(":/translations/hobbycad_" + locale)) {
        app.installTranslator(&translator);
    } else if (translator.load("translations/hobbycad_" + locale)) {
        app.installTranslator(&translator);
    }
    // If neither loads, English strings from tr() are used as-is.

  9.7  Fun / Community Languages
  --------------------------------

  Non-standard languages like Pirate, Lolcat, Shakespearean, etc.
  are welcome as community contributions.  They follow the same
  .ts file format and workflow.  The language name is freeform:

    hobbycad_pirate.ts:      "Arr, open ye BREP file!"
    hobbycad_lolcat.ts:      "I CAN HAZ GEOMETRY?"
    hobbycad_shakespeare.ts: "Pray, save thine document"

  These are listed in the language selector alongside standard
  locales.  The display name comes from the .ts file metadata.

  9.8  Strings That Must NOT Be Translated
  ------------------------------------------

  The following must remain in English regardless of locale:

    - BREP, STEP, STL, IGES (file format names)
    - OCCT, Qt, OpenGL (technology names)
    - Command names in the CLI (help, open, save, exit)
    - File extensions (.brep, .brp, .qss, .qm)
    - Object names (setObjectName values)
    - Debug/log output
    - SPDX identifiers

  9.9  A Front End Without Qt
  ----------------------------

  The library marks strings and translates nothing itself
  (hobbycad/translate.h): a front end installs a translator with
  setTranslator().  The Qt application forwards to
  QCoreApplication::translate; the Qt-free command line has the .ts
  catalogs compiled into it by scripts/ts2cpp.py, generated only for a
  command-line-only build with no Qt (HOBBYCAD_CLI_CATALOGS) and never
  committed.  hobbycad/locale.h decides which language, without Qt:
  HOBBYCAD_LANG, then LC_ALL, LC_MESSAGES and LANG, then the platform's
  own answer (GetUserDefaultLocaleName() on Windows, which sets none of
  those).

  Rules that follow from that seam:

    - It carries no count, so text the library or the command layer can
      reach must not use %n.  Use an explicit count: "Sketches not
      finished: %1", not "%n sketch(es) not finished".
    - A message's key is (context, disambiguation, source).  Never drop
      the disambiguation: 24 groups of messages differ only by it, and a
      key without it shows the right words for the wrong command.
    - A name a person TYPES stays English (constraintTypeName); only the
      name SHOWN is translated (constraintDisplayName).  Never translate
      a keyword, and never interpolate an untranslated name into a
      translated sentence.
    - Numbers in command-line output stay in the C locale, because that
      output is also a script's input.

================================================================================
  10. THEME AND RESOURCE EMBEDDING
================================================================================

  10.1  Resource System Overview
  -------------------------------

  Qt's resource system (.qrc) compiles files into the application
  binary at build time.  This ensures built-in themes and translations
  are always available without requiring external files.

  Resource files are accessed at runtime via the ":/" prefix:

    QFile f(":/themes/default.qss");

  10.2  File Layout
  ------------------

  The resource collection file src/hobbycad/resources/hobbycad.qrc
  compiles in the built-in themes from the top-level resources/ tree
  (aliased, so the runtime paths stay :/themes/default.qss and
  :/themes/darkmode.qss):

    resources/themes/
      default.qss              Platform-native defaults (compiled in)
      darkmode.qss             Dark mode (compiled in)

  Compiled translations (.qm) are built by lrelease into the build
  tree and installed to share/hobbycad/translations/, not embedded.

  No other theme is kept in the tree. A custom theme starts as a copy
  of one of the two built-in files, which list every widget ID with
  its value, and is loaded from disk (10.3).

  10.3  Theme Loading Order (Runtime)
  ------------------------------------

  The application resolves themes in this priority order:

    1. Command-line flag:    --theme /path/to/mytheme.qss
    2. Environment variable: HOBBYCAD_THEME=/path/to/mytheme.qss
    3. User config file:     ~/.config/HobbyCAD/theme.qss
    4. Built-in default:     :/themes/default.qss

  At each step, if the file exists and is readable, it is loaded
  and applied via qApp->setStyleSheet().  The first match wins.

  10.4  Compile-Time vs Runtime Themes
  --------------------------------------

  Built-in themes (resources/themes/):
    - Compiled into the binary via .qrc
    - Always available, no external files needed
    - Versioned with the source code
    - Updated only with new releases

  Custom themes (~/.config/HobbyCAD/theme.qss, HOBBYCAD_THEME or
  --theme):
    - Loaded at runtime from disk
    - Can be modified without rebuilding
    - Distributed separately from the application

  The built-in default.qss and darkmode.qss are kept minimal and
  stable and are the starting point for any custom theme.


================================================================================
  11. LAYERING AND CODE REUSE
================================================================================

  This section exists because the separation below has repeatedly eroded
  in practice.  Treat it as a hard rule, not a preference.

  Why it matters:

    libhobbycad's public API is deliberately Qt-free.  The reason is not
    purity; it is that an alternative front end (wxWidgets, GTK, or a
    headless tool) must remain cheap to build.  That option only stays
    open while the GUI is thin.  Every piece of logic that lives in
    src/hobbycad/ instead of src/libhobbycad/ is work a second front end
    would have to reimplement from scratch.

    A second toolkit build is hypothetical, but the barrier to it should
    stay low.  Keeping logic in the library is how that barrier stays low.


  11.1 WHERE CODE BELONGS
  ------------------------

  Belongs in src/libhobbycad/ (Qt-free):

    - Geometry and math of every kind
    - Sketch entities, constraints, and the solver
    - Document and project model, parameters, features
    - File I/O and format conversion
    - Units, formatting, parsing, validation
    - Tessellation, profile detection, snapping, queries
    - The front-end support layer (11.5): what commands, fields and
      settings exist, and HobbyCAD's default arrangement of them

  Belongs in src/hobbycad/ (Qt-facing):

    - Event handling (mouse, keyboard, focus)
    - Painting and rendering
    - Widget construction and placement, dialogs, QAction objects
      (built from the library's definitions, not written out here)
    - Interaction state (what is selected, what tool is active,
      what is being dragged)
    - Conversion between library types and Qt types at the boundary

  The test to apply: if a wxWidgets front end would need this code,
  it belongs in the library.


  11.2 RULES
  -----------

  1. Before writing geometry or math in src/hobbycad/, search
     src/libhobbycad/ for an existing function.  Start with:

       src/libhobbycad/hobbycad/geometry/utils.h
       src/libhobbycad/hobbycad/geometry/intersections.h
       src/libhobbycad/hobbycad/geometry/algorithms.h
       src/libhobbycad/hobbycad/sketch/
       src/libhobbycad/hobbycad/units.h

  2. If the function exists, call it.  If it nearly exists, extend the
     library version rather than writing a local variant.

  3. Hand-rolled vector math in GUI code is a defect when the library
     already provides it.  In particular:

       std::sqrt(v.x() * v.x() + v.y() * v.y())   ->  geometry::length(v)
       dividing a vector by its own length         ->  geometry::normalize(v)

     geometry/utils.h also provides dot, cross, lengthSquared,
     perpendicular, lerp, vectorAngle, angleBetween, rotatePoint,
     projectPointOntoRay, snapToAngleIncrement, and more.  Check before
     writing.

  4. Do not copy a block of logic to a second location.  If two call
     sites need the same behavior, extract one function and call it
     twice.  A copied block is two things that must now be corrected
     twice, and copies drift.

  5. Prefer a small function or a typed wrapper over a preprocessor
     macro.  Macros defeat the debugger, IDE navigation, and type
     checking; an inline function costs nothing at runtime.  Macros are
     acceptable for repetitive declarative registration tables, where
     the alternative is dozens of near-identical stanzas.


  11.3 CONSOLIDATING GUI CODE INTO THE LIBRARY
  ---------------------------------------------

  When moving code from the GUI into libhobbycad, do not assume the
  library version is the better one.  The GUI copy has usually been
  exercised harder and often carries:

    - Epsilon guards (> 1e-6, > 1e-9) the library version lacks
    - Additional entity types or edge cases
    - Ordering or degeneracy handling learned from real use

  Merge the best of both, then delete the GUI copy.  Blindly replacing
  the GUI code with the existing library function is how working
  behavior gets lost.


  11.4 INTENTIONAL DUPLICATION
  -----------------------------

  Some duplication is deliberate and must NOT be consolidated:

    - The Qt and non-Qt paths in src/libhobbycad/project.cpp and
      parameters.cpp, selected by #if HOBBYCAD_HAS_QT.  These exist so
      the library builds without Qt at all.  Collapsing them would
      break the Qt-free build.

      Note that only the accessor spellings and the JSON type genuinely
      differ between those paths; where the two sides are identical,
      the code should be written once outside the #if rather than
      duplicated inside it.

    - Repetitive declarative registration blocks.  These are data, not
      logic.  Convert them to a table driven by a loop where practical,
      but do not attempt to "de-duplicate" them as if they were
      algorithms.  Commands, key bindings and toolbars are such tables
      in the library now (11.5); do not start a second one in the GUI.


  11.5 THE FRONT-END SUPPORT LAYER: CAPABILITY AND ARRANGEMENT
  -------------------------------------------------------------

  The decisions a front end makes (which commands exist, what a field
  holds, which keys are bound, where a tool sits) live in the library,
  so a second front end, or a rearranged Qt one, does not re-derive
  them.  They come in two tiers, and a new definition goes in exactly
  one of them:

    Capability: what exists and what it does.  Beside its domain:
      hobbycad/commands.h         every command: id, text, icon, what it
                                  acts on, when it is available
      hobbycad/bindings.h         key and mouse binding rules: parsing,
                                  conflicts by context
      hobbycad/settings_schema.h  every preference: key, type, default,
                                  range
      hobbycad/sketch/property_schema.h
                                  an entity's fields, their locks and
                                  point names
      hobbycad/sketch/dimension_field.h
                                  the fields typed while placing geometry
      hobbycad/sketch/edit_session.h
                                  an open sketch's edits, their undo
                                  history, and the checks a new
                                  constraint passes
      hobbycad/sketch/dimension_input.h
                                  typing a value while placing: editing,
                                  locking, expressions
      hobbycad/sketch/placement.h every drawing tool's stages, prompts,
                                  fields, cursor, entity and preview
      hobbycad/sketch/view.h, pick.h, selection.h, handle_drag.h
                                  where the sketch sits on screen, what a
                                  click hits, how the selection changes,
                                  and a handle drag with its undo step
      hobbycad/sketch/transform_form.h
                                  the move/copy form: rows per move type,
                                  what is missing, the point to pick next
      hobbycad/project_session.h (timelineMoveAllowed, timelineActions)
                                  the timeline's order rules and row
                                  actions
      hobbycad/project_files.h    a project folder's file status and its
                                  .gitignore, kept line for line

    Arrangement: where HobbyCAD puts things.  Only in hobbycad/layout/:
      hobbycad/layout/arrangement.h
                                  menus, toolbars, tool groups, variants,
                                  default key bindings
      hobbycad/layout/customization.h
                                  the person's own changes to it, the
                                  hardened reader for their file, and
                                  restore, import and export

  Rules:

  1. The arrangement names capability by id and holds no text of its
     own.  A front end with its own layout replaces the arrangement and
     keeps all of the capability tier.

  2. Includes go one way: layout/ may include capability headers; no
     file outside layout/ may include layout/.  tests/headers checks it.

  3. Text is English at the definition, marked for extraction with
     HOBBYCAD_TRANSLATE_NOOP (or HOBBYCAD_TRANSLATE_NOOP3 with the
     command id as the disambiguation), and translated by the front end
     when shown.  Never compare translated text; compare ids.

  4. The Qt front end builds its menus, toolbars and bindings dialog
     from these (gui/commandtext.h, gui/arrangedtoolbar.h).  A new
     command is one registry entry plus one arrangement line, not a new
     QAction written out by hand.

  5. A key heard by one view (the sketch canvas, the 3D viewport) is a
     Surface binding: the view handles it when it has focus, and menus
     only name it.  Window-wide keys become QAction shortcuts.


================================================================================
  12. SKETCH CANVAS TOOL HANDLERS
================================================================================

  Sketch tool behavior belongs in a SketchToolHandler subclass under
  src/hobbycad/gui/tools/, one per tool, NOT in a switch inside
  SketchCanvas.

  The canvas began as a single large class in which every tool was a
  case label in eight dispatch points.  Handlers are the way out of
  that, and the migration is incremental by design: old and new dispatch
  live side by side, and the app builds and runs after every individual
  tool moves.  There is deliberately never a half-built state.

  This approach was chosen over a parallel second canvas and over a
  ground-up rewrite, and is referred to in discussion as "Plan A" (or
  Route A, after the document that compared the alternatives).  The
  rationale for the routes NOT taken is not repeated here; what follows
  is the contract that binds code in this repository.

  12.1  The Fallthrough Contract
  -------------------------------

  Every hook returns bool:

      true    this handler dealt with the event; the canvas stops.
      false   not handled; the canvas falls through to its existing
              switch, which behaves exactly as it did before.

  That single convention is what lets a migrated tool and an unmigrated
  one coexist.  A tool is migrated by implementing its hooks and then
  DELETING its case labels from the dispatch points it now covers.  The
  old switch shrinks monotonically; when the last tool leaves, the
  switch is empty and is removed.

  applyCreationMode() follows the same contract for creation modes.
  CreationMode values restart at 0 for each tool, so only the owning
  tool can say what a given value means, which is precisely why the
  interpretation belongs in the handler.

  Do NOT add a new per-tool case to a canvas switch.  That grows the
  structure this section exists to remove.  Put it in the handler.

  12.2  Do Not Collapse mousePress And mouseRelease
  --------------------------------------------------

  These are separate hooks and must stay separate.

  Every staged mode accepts two input styles: click-click-click, and
  press-drag-release past a small threshold, detected per stage.  Press
  places a point on click; release places the next one if the user
  dragged.  A single "onClick" abstraction cannot express both, and
  merging them silently deletes drag-through placement, silently
  because everything still compiles, and click-click-click still works,
  so the loss shows up only when someone tries to drag.

  12.3  Handlers Keep No Rules
  -----------------------------

  One instance per tool is created with the canvas and lives as long as
  it does.  Per-tool mode state (the active line mode, circle mode and so
  on) lives on SketchCanvas and is read and written through accessors.
  A handler keeps only what one placement in progress needs and resets
  it when the next begins (the Bezier pen's anchors, a rectangle's kept
  turn); it keeps no rules.

  12.4  Placement Belongs To The Library
  ---------------------------------------

  What a drawing tool does with its clicks (the stages, prompts and
  fields, where the cursor may go, what a lock does, the entity and the
  preview) is sketch/placement.h.  A drawing tool's handler derives from
  PlacementToolHandler, which feeds the canvas's state to those calls and
  paints the preview they return (gui/placementpainter.h); the handler
  adds only how clicks reach it and what its mode is.  A fix to a tool's
  geometry goes in the library, where the preview and the commit share
  it and a test can reach it.
